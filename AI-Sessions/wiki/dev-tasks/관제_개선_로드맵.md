# 관제 대시보드 개선 로드맵 (hawecontrol.com)

## Summary

관제 개선 후보를 **위키에 이미 기록된 미완 과제와 사고 이력만을 근거로** 정리하고 우선순위를 매겼다. 새 기능 아이디어를 얹은 것이 아니라, **이미 적어둔 것 중 무엇을 먼저 할지**를 정하는 문서다.

우선순위 원칙: **되돌릴 수 없는 손실 > 틀린 정보가 화면에 뜨는 것 > 마감이 있는 운영 건 > 기능 확장.**

> **★검증 상태 = draft.** 이 문서는 위키 문서만 읽고 만들었다. 관제 **소스코드와 라이브 화면을 확인하지 않았다**(코드는 원장 PC·VPS에만 있고 저장소에 없음). 따라서 "이미 되어 있는데 문서에 안 적힌" 항목이 섞여 있을 수 있다. **착수 전 실제 상태를 먼저 확인**하고, 확인된 항목은 `active`로 올린다.

## Context

관제는 2026-08 VPS 이전으로 원장 PC 의존을 끊었고, 로그인·역할 권한과 조교 운영 체계까지 올라갔다. 기능은 충분히 쌓였고, 지금 남은 위험은 대부분 **기능 부족이 아니라 데이터 안전성·판정 정확성**에 있다. 실제로 2026-08 한 달 동안 위키에 기록된 사고가 4건이다(자습실 이력 유실 · 빈 명단 미러 덮어쓰기 · 근태 반쪽 표시 · 동명이인 프로필 공유).

## P0 — 데이터 안전 (되돌릴 수 없는 것)

### P0-1. 정본 파일 백업 범위가 `_kiosk_history.json` 하나뿐이다

- **근거**: [[관제_VPS이전_조교운영_2026-08]] §5. 자습실 등원 이력 7월 하순~8/9가 사라졌고 **백업이 없어 복구 불가**였다. 조치로 `adot_hist_backup.sh`(매일 23:20, 30일 보관)를 걸었지만 **그 파일 하나만** 대상이다.
- **문제**: 같은 사고가 나면 못 살리는 파일이 최소 6개 더 있다 — `profiles.json`(시간표·출결·프로필 정본) · `_shifts_2026.json`(근무표·교체 이력) · `_contacts.json`(학생·학부모 번호, 원본은 CRM 엑셀뿐) · `_slot_events.json` · `_staff_att.json` 2벌 · `books.json`. `profiles.json`은 **수동 편집 정본**이라 날아가면 CRM으로도 복원되지 않는다.
- **할 일**: `/opt/adot-dash/`·`/opt/adot-kiosk/`의 JSON 정본을 통째로 묶어 일 1회 백업(30일 보관). `_hist_load(strict=True)` 가드도 같은 방식으로 다른 로더에 확대 적용.
- **검증**: 백업본에서 `profiles.json` 복원 리허설 1회. 복원 후 화면에서 학생 수·시간표 일치 확인.
- **우선순위 이유**: 이 항목만 유일하게 **실패 시 복구 불가**다. 나머지는 전부 나중에 고칠 수 있다.

### P0-2. `_contacts.json` 원본 갱신 절차가 사람 기억에 의존한다

- **근거**: 같은 문서 §3. "**본사 CRM API에는 번호가 없다** — 엑셀이 유일한 소스이므로 학생이 바뀌면 다시 받아 갱신해야 한다."
- **문제**: 갱신 트리거가 없다. 신규생·번호 변경이 조용히 누락되고, 조교가 미등원 학생에게 전화하려는 **그 순간**에 발견된다.
- **할 일**: 조교 보드에 "연락처 파일 최종 갱신일" 표시 + 60일 경과 시 원장에게만 보이는 배지. (알림 신설이 부담이면 표시만이라도.)
- **비고**: 개인정보 파일이므로 화면에는 **날짜만**, 번호는 기존대로 서버에만.

## P1 — 틀린 정보가 화면에 뜨는 것

### P1-1. ★빠른채점 성적이 아직 이름 기준이다 (동명이인 미분리)

- **근거**: [[관제대시보드_2026-07확장]] — "숙제=`HW_BY_ID`. 단어시험=`WT_BY_ID`. **빠른채점 성적은 아직 이름 기준(미분리, TODO)**."
- **문제**: 김민성 2명(우리반 고1 `m1sung0` / 정국쌤반 고2 `kms091206`)의 **성적이 서로 섞여 학생 카드에 표시된다.** 숙제·단어시험·프로필은 전부 ID/`pkey`로 분리했는데 성적만 남았다. 학부모 상담에서 쓰이는 화면이라 **틀린 값이 밖으로 나갈 수 있는 경로**다.
- **할 일**: `/api/student_grades`를 `stuId` 반환으로 확장 → `GR_BY_ID`. 기존 `DUP_NAMES` 집합을 그대로 재사용(중복 이름만 ID 조회, 나머지는 현행 유지 = 기존 데이터 보존).
- **검증**: 두 김민성 카드를 나란히 열어 모의 등급·내신 점수가 각자 것인지 대조. [[판정로직_센티널·타이밍_함정]] ③의 교훈대로 **카드·모달·검색 세 경로 모두** 같은 키를 쓰는지 확인(전에 이 셋이 어긋나 한쪽만 고쳐졌다).
- **우선순위 이유**: 위키에 **유일하게 `TODO`로 명시된 미분리 항목**이고, 동명이인 분리 작업의 마지막 조각이다.

### P1-2. 권한 필터의 파생 쓰기 경로 전수 점검

- **근거**: [[권한필터_파생데이터_덮어쓰기]] — "권한으로 데이터를 걸렀다면, 그 걸러진 데이터를 **다른 곳에 쓰는 경로(동기화·미러·내보내기·집계)** 를 반드시 같이 막아야 한다."
- **문제**: 사고 후 `canMirror()` 게이트를 넣었지만 그건 **`pushSched()` 한 곳**이다. 권한으로 걸러진 명단을 읽는 다른 경로가 있는지는 확인된 바 없다 — 조교 보드 타일 집계(오늘 등원·숙제 미흡 명수), 자습실 `_expected_today()`, 통계 화면이 후보다.
- **할 일**: "권한 필터를 통과한 데이터를 쓰는 함수" 목록을 만들어 한 번에 훑는다. 원장 계정으로 본 값과 조교 계정으로 본 값이 **같아야 하는 지표**(전체 등원 수 등)를 골라 두 계정으로 대조.
- **비고**: 이건 기능 추가가 아니라 **점검**이다. 결과가 "이상 없음"이어도 그 자체가 산출물.

### P1-3. 근태 기록 이원화의 근본 해소 (또는 명시적 수용)

- **근거**: [[기록이_두곳에_생기는_구조]] — 아이패드 키오스크와 관제가 각자 `_staff_att.json`을 쓴다. `_staff_att_all()`로 읽을 때 병합하는 것으로 봉합.
- **현재 상태**: `/staff` 키패드 페이지는 §8-5에서 폐지됐다. 즉 **입력 창구는 아이패드 하나로 이미 줄었다.** 그렇다면 관제 쪽 파일에 새 기록이 쌓일 이유가 남았는지 확인이 필요하다.
- **할 일**: 관제 쪽 `_staff_att.json`에 최근 기록이 계속 생기는지 확인. 안 생기면 **읽기 전용 과거 아카이브로 못 박고** 병합 로직에 그 사실을 주석으로 남긴다. 계속 생기면 어떤 경로인지 찾아 창구를 정말로 하나로 만든다.
- **우선순위 이유**: 봉합은 되어 있어 당장 화면은 맞다. 다만 **다음 사람이 두 파일을 보고 어느 쪽이 정본인지 모른다** — 인수인계 리스크.

## P3 — 기능 확장 (원장 결정 대기 포함)

### P3-1. 요일 고정 업무 — 목요일·각 요일 마감 업무 미수령
- **근거**: §8-1·§9. 오픈 업무 위주로만 채워져 있고 **마감조 업무가 비어 있다.**
- **막힌 지점**: 기술이 아니라 **입력**이다. 원장이 목록을 주면 바로 반영된다.

### P3-2. 블로그 조교 위임 — 원장 착수 결정 대기
- **근거**: §9. 위키 판단은 "주제만으론 부족, **주제 + 꼭 들어갈 3줄 + 소재 위치**까지 주면 가능".
- **만들 것**: 조교 보드 "이번 달 블로그 주제" 카드(원장만 작성, 조교가 집어서 검수 요청). 기존 [[블로그_자동화]] 파이프라인과 붙이면 조교 몫은 초안 검수·사진·발행 대기.
- **선행**: [[SOP_블로그_시험분석글_제작발행]] 준수 여부를 조교가 판단할 수 있는지 — 발행 승인은 원장 고정.

### P3-3. 강의 미수강 판정 — "수강 대상 학생" 구분이 선행
- **근거**: §8-8. "강의를 안 듣는 학생도 있어서 **경고·판정은 넣지 않았다**"(원장 결정). 지금은 "최근 7일 수강 기록 없음"만 담담히 표시.
- **선행 조건**: 명단에 `수강 대상` 플래그. 이게 없으면 조교 보드 타일·자습실 경고를 붙이는 순간 **미대상 학생까지 전원 경고**가 뜬다 — [[판정로직_센티널·타이밍_함정]] ①센티널 0 사고와 정확히 같은 구조.

### P3-4. 시간표 빈칸 일정 — 반복 일정 미지원
- **근거**: §8-7. "반복 일정은 아직 없음(다음 주 상담은 다음 주 표에서 다시 등록)."
- **주의**: 키가 **날짜+시간**인 이유가 "요일로 잡으면 매주 반복돼 지난 주 표에도 나온다"였다. 반복을 넣는다면 **생성 시점에 날짜를 펼쳐 저장**하는 방식이어야 과거 표가 오염되지 않는다.

## 별도 — 보안 관찰 (원장 판단 필요)

### 아이디 = 비밀번호 규칙

- **근거**: §1 계정표 — `yunasong1120` / `zlddbsk9151` / `jjk2506` / `gihyes25` / `lyj6185` 전부 **아이디와 비밀번호가 같다**(문서에 "아이디=비밀번호 규칙 동일"로 명시).
- **관찰**: 인증 자체는 견고하다(pbkdf2-sha256 12만회 + HMAC 서명 쿠키). 약한 건 **비밀번호 값**이다. 조교 아이디는 근무표·보드에 노출되므로, 아이디를 본 사람은 곧 비밀번호를 안 것이 된다.
- **무엇이 걸리나**: 로그인 시 관제 전체 — 학생 명단·출결·성적·**연락처 조회**까지 도달한다. 개인정보 열람 경로가 열려 있다.
- **선택지**:
  - (a) 현행 유지 — 조교 회전이 잦고 기억 부담이 크다는 실무 판단. **단, 왜 유지하는지 위키에 결정으로 남긴다.**
  - (b) 최초 로그인 시 비밀번호 변경 강제.
  - (c) 로그인 실패 횟수 제한(현재 문서상 없음) — 가장 적은 노력으로 무차별 대입만 막는 절충안.
- **판단**: 이건 **기술 결정이 아니라 원장 결정**이다. 여기서는 상태만 기록한다. → 결정되면 [[디리스킹_장부]]에 등재.
