# 관제 로그인을 본사(에이닷) 계정으로 — 설계

## Summary

관제 로그인을 **본사 CRM(`crm.adotenglish.com`) 계정 인증**으로 바꾼다. 조교들도 본사 계정을 보유하고 있음이 확인되어(원장, 2026-08-17) C안으로 진행한다.

핵심 설계 방침 세 줄:

1. **본사는 "이 사람이 맞다"만 판정한다.** 역할·반 배정·차단 여부는 계속 우리 테이블이 정본이다.
2. **본사 비밀번호와 OTP 시크릿을 저장하지 않는다.** 검증하고 즉시 버린다.
3. **본사가 죽어도 원장은 들어갈 수 있다.** 로컬 비상 열쇠를 남긴다.

> **status: draft** — 아래 §5 미지수 4건은 **실제 호출로 확인해야** 확정된다. 특히 조교 계정에 OTP가 걸려 있는지에 따라 §3 UX가 갈린다.

## Context

기존 상태: 계정 5개가 **아이디 = 비밀번호**([[관제_VPS이전_조교운영_2026-08]] §1). 인증 방식 자체는 견고하나(pbkdf2-sha256 12만 회 + HMAC 서명 쿠키 30일) 비밀번호 값이 사실상 공개다. 조교 아이디는 근무표·보드에 노출되므로, 아이디를 본 사람은 학생 명단·성적·**연락처 조회**까지 도달할 수 있다.

원장 결정: 자체 비밀번호 발급(A안) 대신 **본사 계정 연동**(C안). 근거 = 조교가 이미 본사 계정을 쓰므로 비밀번호를 하나 더 만들지 않는다.

## 1. 인증 흐름

```
브라우저(hawecontrol.com 로그인 폼)
  uid · passwd · otp(6자리)
   ↓  HTTPS, 같은 출처
dash_server
   ① 우리 쪽 실패횟수 확인  ← ★본사에 도달하기 전에 막는다
   ② _accounts.json 조회 (uid 존재? disabled?)
   ↓  내부망
exam_server(8097)
   ③ POST /inc/login.php?m=login&debugx=1  (ttype · uid · passwd · otp)
   ④ 응답 첫 글자가 '{' 인가로 판정   ← ★본사는 실패해도 200+HTML
   ⑤ PHPSESSID 즉시 폐기 (검증 전용, 데이터 조회 세션과 분리)
   ↓
dash_server
   ⑥ 우리 서명 쿠키(adot_sess) 발급 — 역할·반은 _accounts.json에서
```

### 각 단계에서 지켜야 할 것

- **④ 판정을 상태코드로 하면 안 된다.** [[본사CRM_API_연동구조]] §1에 이미 적힌 함정 — 본사는 세션이 끊겨도 **200 OK + 로그인 HTML**을 준다. 로그인 검증도 같은 규칙(`첫 글자 == '{'`)을 쓴다. 이걸 빠뜨리면 **비밀번호가 틀려도 통과**하는 최악의 버그가 난다.
- **⑤ 본사 세션을 사용자 세션으로 쓰지 않는다.** 로그인 검증용 세션은 확인 즉시 버린다. 데이터 조회용 원장 세션(`_crm_login`이 유지하는 것)과 **절대 섞지 않는다** — 섞으면 조교 로그인이 원장 세션을 갈아치워 데이터 조회가 통째로 흔들린다.
- **⑥ 권한은 본사가 아니라 우리가 정한다.** 본사 인증에 성공해도 `_accounts.json`에 `disabled:true`면 거부한다(예: 송유나 조교 8월말 잠금 — §8-5). 본사 계정이 살아 있다는 이유로 잠금이 풀리면 안 된다.

## 2. 저장하지 않는 것 (설계 원칙)

| 항목 | 처리 |
|---|---|
| 본사 비밀번호 | **저장 금지.** 메모리에서 검증 후 폐기. 로그·에러 메시지·예외 트레이스에도 남기지 않는다 |
| 본사 OTP 시크릿 | **수집 금지.** 사용자가 매번 6자리를 직접 입력한다. 시크릿을 우리가 보관하면 본사 2단계 인증이 무력화된다 |
| 본사 PHPSESSID(검증용) | 판정 직후 폐기 |
| 우리 비밀번호 해시 | 원장 비상 계정만 유지(§4) |

기존 원칙 [[본사CRM_API_연동구조]] §3 "비밀은 서버에 갇힌다"를 깨지 않는다. 사용자 비밀번호는 **서버를 스쳐 지나갈 뿐 머무르지 않는다.**

## 3. ★OTP를 근무일마다 입력하게 되는 문제

### 왜 생기나

[[관제_VPS이전_조교운영_2026-08]] §8-5: **퇴근을 찍으면 관제 로그인이 끊긴다**(쿠키 삭제, 원장 지시 A안). 즉 조교는 30일 쿠키가 있어도 **근무일마다 새로 로그인**한다. 여기에 OTP를 걸면 근무 시작마다 인증 앱을 열어야 한다.

조교 근무는 주 여러 회다(9월 주력 = 양지혜 오픈 · 이윤주 마감 · 이유나 금토). 곱하면 마찰이 작지 않다.

### 선택지

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **3-a** | 매 로그인 본사 인증 + OTP 입력 | 가장 단순·본사가 항상 정본 | 근무일마다 인증 앱. 본사 장애 = 전원 차단 |
| **3-b** | **최초 1회만 본사 인증으로 신원 확인 → 그 자리에서 관제 전용 비밀번호 본인 설정. 이후 일상 로그인은 관제 비밀번호** | OTP는 최초 1회. 본사 장애와 무관. 비밀번호는 본인만 앎 | 관제 비밀번호가 별도로 하나 생김(단, 본인이 정함) |
| **3-c** | 3-a + 기기 기억(신뢰 기기 30일) | 새 기기에서만 OTP | "퇴근 시 로그아웃" 취지와 충돌 소지 — 기기 기억은 유지하되 세션만 끊는 설계 필요 |

**권고: 3-b.** 원장님 목표(조교가 이미 아는 계정으로 들어온다 / 비밀번호가 아이디와 같지 않다)를 둘 다 만족하면서, 본사 장애가 로그인을 잠그는 위험을 피한다. 신원의 출처는 여전히 본사다.

3-a로 가더라도 §4 폴백은 반드시 있어야 한다.

## 4. 폴백 — 본사가 깨져도 들어갈 수 있어야 한다

[[본사CRM_API_연동구조]] §5(추측 아닌 설계상 사실): "공식 API가 아니라 화면 내부 주소를 빌려 쓰므로 **본사가 화면을 개편하면 조용히 깨진다.**"

지금 깨지면 데이터 패널만 "조회 실패"다. 로그인을 걸면 **관제·조교 보드·자습실 전체가 잠긴다.** 그래서:

1. **원장 계정은 로컬 비밀번호를 병행 유지**한다(비상 열쇠). 본사 응답이 없으면 로컬로 로그인.
2. 본사 응답 실패 시 화면에 **"본사 인증 서버 응답 없음"** 을 명시한다. 비밀번호 오류와 구분되게 — 안 그러면 조교가 자기 비밀번호를 의심하며 계속 재시도하고, 그게 §5의 계정 잠금으로 이어진다.
3. 이미 로그인된 세션은 본사 장애와 무관하게 유지된다(우리 서명 쿠키라 본사를 다시 묻지 않음). 장애가 나도 **근무 중인 사람은 안 끊긴다.**
4. **출퇴근은 원래 로그인 밖**이다(아이패드 키오스크, §2). 로그인이 통째로 막혀도 **근태 기록은 계속 남는다.** 이건 이미 확보된 안전판이다.

## 5. 착수 전 실측할 미지수 4건

위키만으로는 확정할 수 없다. **조교 계정 1개(예: 양지혜)로 실제 왕복 호출**해서 확인한다.

1. **조교 계정에 OTP가 걸려 있나?** 원장 계정만 2단계 인증일 수 있다. 안 걸려 있으면 §3 문제 자체가 사라진다(가장 좋은 결과).
2. **`ttype=2`가 조교 직급에도 맞나?** 위키에 적힌 값은 원장 로그인 기준이다. 직급별로 다를 수 있다.
3. **로그인 응답이 직급을 주나?** [[본사CRM_API_연동구조]] §2에 `/inc/studentManage/authorization`이 200으로 `jik: 원장`·`week: Y`를 준다고 되어 있다. 이걸로 역할을 자동 매핑할 수 있는지 — **가능해도 우리 테이블을 정본으로 유지**한다(§1-⑥). 자동 매핑은 참고용.
4. **본사 계정 잠금 정책** — 몇 회 실패에 잠기는지 모른다. 모르면 우리 제한을 **보수적으로 3회**로 잡는다.

### 확인 방법

원장님이 브라우저 개발자도구에서 조교 계정 로그인의 cURL을 복사해 주시는 게 가장 빠르다. [[본사CRM_API_연동구조]] §2의 교훈 그대로 — **"원장 브라우저 cURL 제공이 30분 추측보다 빨랐다"**(`sort=not_set` 건).

## 6. 실패 횟수 제한 (본사 계정 보호)

[[본사CRM_API_연동구조]] §1: "로그인 실패가 반복돼 **계정이 잠기지 않도록** 실패 후 30초 백오프."

지금은 서버가 원장 계정 하나로만 로그인하니 백오프면 충분했다. 사용자가 직접 치기 시작하면 **오타가 본사 계정 실패로 쌓인다.** 조교가 본사 계정을 잠그면 관제뿐 아니라 **본사 업무까지 막힌다.**

→ **우리 쪽에서 먼저 막는다**(§1-①). 아이디당 3회 실패 시 10분 잠금, 그동안 본사에 요청을 보내지 않는다. 잠금은 우리 서버 메모리·파일에만 기록한다.

## 7. 전환 계획

1. **원장 계정 먼저** 전환·검증. 로컬 비상 열쇠가 동작하는지 함께 확인.
2. 조교는 **근무 없는 날**에 전환하고 미리 공지. 3-b라면 최초 연결을 원장님 입회하에 1명씩.
3. 전환 중에도 **근태는 안 막힌다**(아이패드 키오스크). 막히는 건 조교 보드·관제 화면.
4. 정국쌤(`jjk2506`)도 같은 절차. 본사 계정 보유 여부 확인 필요.
5. 전환 완료 후 `_관제_계정_비밀번호.txt`(로컬 평문 목록)를 **정리**한다 — 더 이상 유효하지 않은 값이 남아 오해를 부른다.

## 8. 검증 (완료 판정 기준)

[[리뷰기준]]에 따라 작동 증명 없이 완료 처리하지 않는다.

- [ ] 올바른 아이디·비밀번호(+OTP) → 로그인 성공, 역할·반이 기존과 동일하게 적용
- [ ] **틀린 비밀번호 → 반드시 거부** (§1-④ 첫 글자 판정이 실제로 걸러내는지 — 이게 제일 중요한 케이스)
- [ ] OTP 누락·오입력 → 거부, 메시지가 비밀번호 오류와 구분됨
- [ ] `disabled:true` 계정 → 본사 인증 성공해도 거부
- [ ] 3회 실패 → 10분 잠금, **그동안 본사에 요청이 나가지 않음**(로그로 확인)
- [ ] 본사 응답 없음(강제 재현) → "본사 인증 서버 응답 없음" 표시 + 원장 로컬 로그인 동작
- [ ] 로그인 검증이 **데이터 조회용 원장 세션을 건드리지 않음** — 조교 로그인 직후 학생 카드 강의 진도가 정상 조회되는지
- [ ] 조교 로그인 착지 화면이 기존대로 조교 보드(§8-4)

## 9. 남는 리스크 (수용 여부는 원장 판단)

- 본사 개편 시 로그인이 깨진다 → §4 폴백으로 완화하되 **없어지지는 않는다.**
- 사용자 비밀번호가 우리 서버를 경유한다(3-a인 경우) → 3-b면 최초 1회로 축소된다.
- 근본 해결은 [[본사CRM_API_연동구조]] §5에 이미 적혀 있다: **본사에서 정식 읽기 전용 API 계정**을 받는 것. 본사 방문·기술 협상 때 이 문서도 함께 근거로 쓴다.
