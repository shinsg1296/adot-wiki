# 관제 로그인을 본사(에이닷) 계정으로 — 설계 (3-b 확정)

## Summary

관제 로그인의 **아이디 = 비밀번호** 규칙을 폐기하고, **본사 CRM(`crm.adotenglish.com`) 계정으로 신원을 확인**하는 방식으로 바꾼다. 조교들도 본사 계정을 보유하고 있음이 확인되어(원장, 2026-08-17) C안으로 진행하며, 방식은 **3-b(최초 1회 연결)** 로 확정한다.

### 3-b가 무엇인가

- **최초 1회**: 본사 아이디·비밀번호(+OTP)로 인증 → 성공하면 그 자리에서 **관제 전용 비밀번호를 본인이 설정**
- **이후 일상 로그인**: 관제 비밀번호만. 본사에 요청이 나가지 않는다
- **비밀번호를 잊으면**: 본사 계정으로 다시 연결하면 끝. **원장이 임시 비밀번호를 발급할 일이 없다**

### 왜 3-b인가 (3-a 대비)

| | 3-a 매번 본사 인증 | **3-b 최초 1회** |
|---|---|---|
| OTP 입력 빈도 | **근무일마다** (퇴근 시 로그아웃이라 매 근무 재로그인) | 최초 1회 + 비밀번호 분실 시 |
| 본사 장애 시 | **전원 로그인 불가** | 일상 로그인 영향 없음 |
| 본사 계정 잠금 위험 | 오타가 매번 본사로 감 | 연결·재설정 때만 |
| 본사 비밀번호 경유 | 매 로그인 | 최초 1회 |

원장님 목표(조교가 이미 아는 계정을 쓴다 / 비밀번호가 아이디와 같지 않다)를 둘 다 만족하면서, [[본사CRM_API_연동구조]] §5의 알려진 취약점(본사 개편 시 조용히 깨짐)을 로그인 경로에서 떼어낸다.

> **status: draft** — §6 미지수 4건은 **실제 호출로 확인해야** 확정된다.

## Context

기존 상태: 계정 5개가 아이디 = 비밀번호([[관제_VPS이전_조교운영_2026-08]] §1). 인증 방식 자체는 견고하나(pbkdf2-sha256 12만 회 + HMAC 서명 쿠키 30일) **비밀번호 값이 사실상 공개**다. 조교 아이디는 근무표·보드에 노출되므로, 아이디를 본 사람은 학생 명단·성적·**연락처 조회**까지 도달한다.

## 1. 두 갈래 흐름

### 1-A. 최초 연결 (계정당 1회, 그리고 비밀번호 재설정 시)

```
로그인 화면 "본사 계정으로 연결하기"
  본사 uid · passwd · otp(있다면)
   ↓
dash_server
   ① 우리 쪽 실패횟수 확인   ← ★본사에 도달하기 전에 막는다
   ② _accounts.json 조회 (uid 존재? disabled?)
   ↓ 내부망
exam_server(8097)
   ③ POST /inc/login.php?m=login&debugx=1  (ttype · uid · passwd · otp)
   ④ 응답 첫 글자가 '{' 인가로 판정   ← ★상태코드로 판정 금지
   ⑤ PHPSESSID 즉시 폐기 (검증 전용)
   ↓
dash_server
   ⑥ 관제 비밀번호 설정 화면 (2회 입력, §2 요건)
   ⑦ _accounts.json 에 저장: pw_hash · linked_uid · linked_at
   ⑧ 우리 서명 쿠키 발급 → 역할별 착지 화면
```

### 1-B. 일상 로그인 (연결 이후)

```
로그인 화면
  아이디 · 관제 비밀번호
   ↓
dash_server
   ① 실패횟수 확인 (5회/10분)
   ② pw_hash 검증 (pbkdf2-sha256 12만 회, 기존 그대로)
   ③ disabled 확인
   ④ 우리 서명 쿠키 발급
   ※ 본사에 요청이 나가지 않는다
```

### 각 단계에서 지켜야 할 것

- **④ 판정을 상태코드로 하면 안 된다.** [[본사CRM_API_연동구조]] §1의 함정 — 본사는 세션이 끊겨도 **200 OK + 로그인 HTML**을 준다. 반드시 `응답 첫 글자 == '{'` 로 판정한다. 빠뜨리면 **비밀번호가 틀려도 연결에 성공**하는 최악의 버그가 난다. 3-b에서는 이 순간이 신원 확인의 **유일한 관문**이라 더 치명적이다.
- **⑤ 본사 세션을 사용자 세션으로 쓰지 않는다.** 검증용 세션은 확인 즉시 버린다. 데이터 조회용 원장 세션(`_crm_login`이 유지하는 것)과 **절대 섞지 않는다** — 섞으면 조교가 연결하는 순간 원장 세션이 갈아치워져 학생 카드 강의 진도 조회가 통째로 흔들린다.
- **⑥ 권한은 본사가 아니라 우리가 정한다.** 본사 인증에 성공해도 `_accounts.json`에 `disabled:true`면 거부한다(예: 송유나 조교 8월말 잠금 — §8-5). 본사 계정이 살아 있다는 이유로 잠금이 풀리면 안 된다.

## 2. 관제 비밀번호 요건

최소한만 건다. 조교 5명 규모에 복잡한 정책은 오히려 메모지를 부른다.

- 8자 이상
- **아이디와 같으면 거부** — 이게 애초에 고치려는 문제다. 명시적으로 막지 않으면 그대로 돌아간다
- 본사 비밀번호와 같은지는 **확인할 수 없다**(우리가 저장하지 않으므로). 안내 문구로만: "본사 비밀번호와 다르게 정해 주세요"
- 만료·주기 변경 없음

## 3. 저장하지 않는 것 (설계 원칙)

| 항목 | 처리 |
|---|---|
| 본사 비밀번호 | **저장 금지.** 메모리에서 검증 후 폐기. 로그·에러 메시지·예외 트레이스에도 남기지 않는다 |
| 본사 OTP 시크릿 | **수집 금지.** 연결할 때 사용자가 6자리를 직접 입력한다. 시크릿을 우리가 보관하면 본사 2단계 인증이 무력화된다 |
| 본사 PHPSESSID(검증용) | 판정 직후 폐기 |
| 관제 비밀번호 | 해시만 저장(pbkdf2-sha256 12만 회, 기존 방식 그대로) |
| `linked_uid` · `linked_at` | 저장. **누가 언제 어떤 본사 계정으로 연결했는지**는 남겨야 추적된다 |

[[본사CRM_API_연동구조]] §3 "비밀은 서버에 갇힌다"를 깨지 않는다. 사용자 비밀번호는 **서버를 스쳐 지나갈 뿐 머무르지 않는다.**

## 4. 전환 시점의 함정 — 기존 비밀번호를 반드시 무효화한다

★**이걸 빠뜨리면 보안이 하나도 개선되지 않는다.**

연결 기능만 만들고 기존 `아이디=비밀번호`를 살려두면, 조교가 연결하지 않는 한 예전 비밀번호로 계속 들어와진다. 그러면 취약점은 그대로다.

- 전환 시 전 계정의 `pw_hash`를 **비우고** `link_required: true`로 표시
- 그 상태의 계정은 **로그인 폼이 아니라 연결 화면으로만** 진입 가능
- 연결을 마쳐야 비로소 일상 로그인이 열린다

## 5. 폴백 — 본사가 깨져도 막히지 않는다

[[본사CRM_API_연동구조]] §5(추측 아닌 설계상 사실): "공식 API가 아니라 화면 내부 주소를 빌려 쓰므로 **본사가 화면을 개편하면 조용히 깨진다.**"

3-b에서 본사 장애가 막는 것은 **최초 연결과 비밀번호 재설정뿐**이다. 이미 연결한 사람의 일상 로그인은 영향받지 않는다. 그래도 남는 대비:

1. **원장 계정은 로컬 비밀번호를 병행 유지**한다(비상 열쇠). 전환 첫날 본사가 죽어도 원장은 들어간다.
2. 연결 실패 시 화면에 **"본사 인증 서버 응답 없음"** 을 명시한다. 비밀번호 오류와 구분되게 — 안 그러면 조교가 자기 비밀번호를 의심하며 재시도하고, 그게 본사 계정 잠금으로 이어진다.
3. 이미 로그인된 세션은 본사와 무관하게 유지된다(우리 서명 쿠키).
4. **출퇴근은 원래 로그인 밖**이다(아이패드 키오스크, §2). 로그인이 통째로 막혀도 **근태 기록은 계속 남는다.** 이미 확보된 안전판.

## 6. 착수 전 실측할 미지수 4건

위키만으로는 확정할 수 없다. **조교 계정 1개(예: 양지혜)로 실제 왕복 호출**해서 확인한다.

1. **조교 계정에 OTP가 걸려 있나?** 원장 계정만 2단계 인증일 수 있다. 안 걸려 있으면 연결 화면에서 OTP 칸을 빼면 된다.
2. **`ttype=2`가 조교 직급에도 맞나?** 위키의 값은 원장 로그인 기준이다. 직급별로 다를 수 있다.
3. **로그인 응답이 직급을 주나?** [[본사CRM_API_연동구조]] §2에 `/inc/studentManage/authorization`이 200으로 `jik: 원장`·`week: Y`를 준다고 되어 있다. 역할 자동 매핑 가능성 확인용 — **가능해도 우리 테이블을 정본으로 유지**한다(§1-⑥). 자동 매핑은 참고값.
4. **본사 계정 잠금 정책** — 몇 회 실패에 잠기는지 모른다. 모르면 연결 화면 제한을 **보수적으로 3회**로 잡는다.

### 확인 방법

원장님이 브라우저 개발자도구에서 **조교 계정 로그인의 cURL**을 복사해 주시는 게 가장 빠르다. [[본사CRM_API_연동구조]] §2의 교훈 그대로 — "원장 브라우저 cURL 제공이 30분 추측보다 빨랐다"(`sort=not_set` 건).
필요한 것은 **필드 이름과 `otp` 칸의 유무**지 값이 아니다. 비밀번호 자리는 가려서 줘도 된다.

## 7. 실패 횟수 제한 — 경계가 두 개다

| 화면 | 제한 | 이유 |
|---|---|---|
| **연결 화면**(본사로 나감) | 아이디당 **3회 / 10분** | [[본사CRM_API_연동구조]] §1 — 실패 반복 시 본사 계정이 잠긴다. 조교가 본사 계정을 잠그면 **관제뿐 아니라 본사 업무까지 막힌다.** 잠금 동안 본사에 요청을 보내지 않는다 |
| **일상 로그인**(우리 안에서 끝) | 아이디당 **5회 / 10분** | 무차별 대입 방지. 본사와 무관하므로 조금 느슨해도 된다 |

잠금 기록은 우리 서버에만 남긴다.

## 8. 전환 계획

1. **원장 계정 먼저** 연결·검증. 로컬 비상 열쇠(§5-1)가 동작하는지 함께 확인.
2. 조교는 **근무 없는 날**에 전환하고 미리 공지. 최초 연결은 원장님 입회하에 **1명씩** — 첫 사람에서 문제가 나면 거기서 멈춘다.
3. 전환 중에도 **근태는 안 막힌다**(아이패드 키오스크). 막히는 건 조교 보드·관제 화면.
4. 정국쌤(`jjk2506`)도 같은 절차. **본사 계정 보유 여부 확인 필요.**
5. 송유나 조교는 8월말 잠금 예정(§8-5)이므로 **연결 대상에서 제외**한다. 남은 근무(8/18·19·24·25·26·31) 동안 어떻게 할지는 원장 판단 — 잠금이 임박했으니 연결을 건너뛰고 기존 상태로 두는 편이 단순하다.
6. 전환 완료 후 `_관제_계정_비밀번호.txt`(로컬 평문 목록)를 **정리**한다. 더 이상 유효하지 않은 값이 남아 오해를 부른다.

## 9. 검증 (완료 판정 기준)

[[리뷰기준]]에 따라 작동 증명 없이 완료 처리하지 않는다.

**최초 연결**
- [ ] 올바른 본사 계정 → 연결 성공, 비밀번호 설정 화면 진입
- [ ] **틀린 본사 비밀번호 → 반드시 거부** (§1-④ 첫 글자 판정이 실제로 걸러내는지 — **가장 중요한 케이스**)
- [ ] OTP 누락·오입력 → 거부, 메시지가 비밀번호 오류와 구분됨
- [ ] `disabled:true` 계정 → 본사 인증 성공해도 거부
- [ ] 연결 3회 실패 → 10분 잠금, **그동안 본사에 요청이 나가지 않음**(로그로 확인)
- [ ] 연결이 **데이터 조회용 원장 세션을 건드리지 않음** — 조교 연결 직후 학생 카드 강의 진도가 정상 조회되는지

**일상 로그인**
- [ ] 설정한 비밀번호로 로그인 성공, 역할·반이 기존과 동일하게 적용
- [ ] 비밀번호를 아이디와 같게 설정하려 하면 거부(§2)
- [ ] 연결 안 한 계정(`link_required`)은 **예전 비밀번호로 못 들어감**(§4)
- [ ] 로그인 시 **본사로 요청이 나가지 않음**(로그로 확인) — 3-b의 핵심 이득
- [ ] 조교 로그인 착지 화면이 기존대로 조교 보드(§8-4)
- [ ] 퇴근 찍으면 로그아웃되고, 재로그인 시 **OTP를 묻지 않음**(§8-5와 3-b가 맞물리는 지점)

**재설정**
- [ ] 비밀번호 분실 → 본사 계정으로 재연결 → 새 비밀번호로 로그인

## 10. 남는 리스크 (수용 여부는 원장 판단)

- **본사 계정이 죽어도 관제는 살아 있다.** 3-b는 최초 1회만 본사를 확인하므로, 조교 퇴사로 본사 계정이 정지돼도 관제 비밀번호는 유효하다. → **계정 종료는 계속 원장이 `disabled:true`로 관리**한다(이미 하고 있는 방식, §8-5). 주기적 재연결 강제는 5명 규모에 과하다고 판단해 넣지 않는다.
- **본사 개편 시 연결·재설정이 막힌다.** 일상 로그인은 무사하나, 그 기간에 비밀번호를 잊은 사람은 원장이 직접 손봐야 한다.
- 근본 해결은 [[본사CRM_API_연동구조]] §5에 이미 적혀 있다: **본사에서 정식 읽기 전용 API 계정**을 받는 것. 본사 방문·기술 협상 때 이 문서도 함께 근거로 쓴다.
